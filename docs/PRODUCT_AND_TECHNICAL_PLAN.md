# Hidan Club：Swift 街舞学习应用调研与实施方案

日期：2026-09-09。目标：建立能帮助个人持续练习、理解动作并回看证据的原生街舞学习工具。用户已确认 Mac 优先、后续扩展 iPhone / iPad；舞种与路线希望全部覆盖。原创练习卡从 Hip-Hop、Popping、Locking、House 展开；新增的 AIST++ 动作参考覆盖全部 10 个源舞种。资料库覆盖范围不等于已审核的课程或能力分级，成人基础站立练习仍是原型训练计划的适用范围假设。

## 0.3 当前交互范围

训练台以实时摄像头捕捉和动作示范为核心，支持并排、两个独立显示模式及透明叠加。AIST 内置计划按每段真实示范驱动。上传视频的主用途是捕捉二维动作模型、形成可保存的连续片段编排并直接跟练；原视频回放用于核对。二维检测不冒充三维重建、动作分类或质量评分。实现与边界见 [实时训练台](TRAINING_STUDIO.md)。

## 1. 结论与产品定位

这个应用可以做，而且不需要先训练一个大型模型。优先完成学习闭环：**选择目标 → 看示范 → 分解与慢练 → 跟拍 → 回看 → 记录感受 → 下次复习**。SwiftUI、AVFoundation、Vision 和本地存储已经能承载核心体验。先把内容来源、训练状态、媒体控制与视频观测做扎实，之后才有可靠的训练数据和评分研究基础。

AI 可以估计身体关键点，也可以在有标注的数据上学习有限动作类别；但单目骨架不是重心、接触力或舞感真值。不能把骨架置信度变成“动作完成度 92%”，也不能因为生成的视频看起来像舞蹈，就把它当可模仿的教学动作。

建议的差异化是：个人动作档案、完整时间戳观察、节拍练习、可解释的训练安排与本地隐私。暂不以课程数量或泛化到所有街舞的 AI 评分竞争。

本轮已实际下载 AIST++ 完整 3D 标注，得到 **1,408 条序列、1,123,873 个独立时间帧、10 个舞种**，原始与官方优化两层以 Float64 全帧保留。另接入 100 个基础动作原名元数据。3D 动作库、检索/收藏、逐帧/A–B/八拍练习、连续片段导出及训练计划导入是本轮界面完善范围，软件验收单独记录，不用数据校验结果代替。

## 2. 现有学习产品带来的设计依据

[STEEZY 官方产品页](https://www.steezy.co/)实际列出前后视角、循环、镜像、变速、分段标签与相机对照。这支持把这些功能当作学习界面的优先项，但没有证明单一交互能保证学习成效。它的课程与视频不能因为可在线播放就自动内置本应用，授权核查见[资源调研](research/dance-resources.md)。

街舞也不宜归为单一动作清单。Hip-Hop 的 groove、Popping 的身体分离与控制、Locking 的停顿与表现、House 的持续律动应分路线学习。第一版 16 个原创文字练习卡用于产品导航，不冒充完整传统动作定义或经教练审核的课程。下阶段需要有经验舞者校对命名、文化语境、示范和常见错误。

建议内容层级：

1. **音乐感知**：找到脉冲、辨认八拍、体验重拍和节奏变化。
2. **身体基础**：柔和膝屈伸、重心转移、身体分离、自然呼吸。
3. **风格基础**：先在一种风格内建立节奏感与动作语言。
4. **动作连接**：两个熟悉动作、四组八拍、方向与手臂变化。
5. **自主表达**：freestyle、选择音乐、记录自己的偏好与问题。

这是待教师验证的产品学习框架，不是已证实的统一教学次序。

## 3. 数据与素材：哪些能用

“资源数据库”需要分成动作数据集、教学内容、音乐素材和应用业务数据库四层；它们的许可与用途不同。

| EDGE | 音乐条件舞蹈生成技术参考 | 代码 MIT，权重/源数据范围另查；CUDA 环境也不等于可直接在 Swift 端运行 | 研究路线，未安装/转换模型 |

逐资产许可、直接证据、来源 URL 与访问状态见 [dance-resources.md](research/dance-resources.md) 和 [dance-resources.json](research/dance-resources.json)。完整 3D 源归档、相机、划分与质量清单已经下载，源哈希/CRC 和所有坐标无损校验见 [AIST_DATASET.md](AIST_DATASET.md)。原视频、图像、音乐和模型权重未下载。

官网 **10,108,015** 统计的是多机位对应图像；当前独立三维帧数由 1,408 个 `cAll` 文件累加得到，不能混算。官网不提供单独全量静态图像包，对应图像需从 AIST 视频解码；原媒体的永久 URL、条款、表单和精确时间对齐方案见 [专项核查](research/aist-images-and-counts.md)。官方 60 FPS 转图流程会重采样，本项目不自动套用，后续保留原视频全部帧及 PTS，并另建完整标注时间轴的显示映射。

## 4. AI 的可行性分层

| 层级 | 能否做 | 数据/验证需求 | 原型状态 |
| --- | --- | --- | --- |
| 2D 身体关键点 | Apple Vision 现成可用 | 全身取景、方向校正、遮挡/多人/衣物场景核查 | 已实现全帧提取、保存二维模型编排、直接跟练及实时相机关节观察 |
| 3D 动作参考 | 现成 AIST++ 标注可直接使用 | 来源坐标、质量标记、全帧保留、显示变换分离 | 全量数据已安装校验；本轮完善参考浏览与训练接入 |
| 从用户视频估计 3D 姿态 | macOS 14 / iOS 17 起可研究 | 深度来源、尺度与接触误差验证 | 尚未接入；已有 3D 参考不代表用户视频已能恢复 3D |
| 舞步名称/动作分段 | 有监督时序模型可做有限类别 | 专家定义标签，负例，跨舞者独立测试 | 未训练；100 个基础名称来自官方 metadata，属于来源标签 |
| 节拍/动作时序比较 | 明确动作和对齐条件后可研究 | beat/downbeat 标签、镜像语义、允许的风格差异 | 原创节拍八拍显示；未自动分析导入歌曲 |
| 纠错与质量评分 | 需要专门评估模型 | 教师量表、标注一致性、误导反馈评估 | 暂不提供 |
| 动作组合设计 | 已掌握动作库 + 约束即可落地 | 先修/BPM/冲击检查，舞者复核连接 | 已实现四组八拍规则草稿 |
| 自由生成 3D 编舞 | 存在研究系统 | 权重与数据许可、接触/碰撞/风格/人体可做性、教师审核 | 后期实验，不做首版承诺 |

[Apple Action Classifier 文档](https://developer.apple.com/documentation/createml/creating-an-action-classifier-model)建议每动作至少 50 个示例；[数据采集指南](https://developer.apple.com/documentation/createml/gathering-training-videos-for-an-action-classifier)要求考虑负例。这只是起始建议，不是街舞分类准确率保证。建议先选 3–5 个边界明确的站立任务，以舞者和拍摄 session 划分训练/验证/测试，避免同一视频切片泄漏。报告每类 precision/recall、混淆矩阵、拒识率、不同身体/衣物/视角的结果，先不承诺数值门槛。

质量反馈要分维度，例如某个明确动作中的落点时刻、左右顺序、参考相位与可见关节轨迹。DTW 可以做速度不同的序列对齐，但会把节拍错误对齐掉，不能将对齐距离直接当节奏评分。2D 角度也受视角影响。评价应分别保留原始时间差、允许的动作变化与检测不确定性。

## 5. 动作模型与数据库设计

长期模型应按观测、含义和教学评价分层：

```text
MoveDefinition ──< ReferenceTake ──< PoseSequence ──< PoseFrame
       │                  │                 │
       ├── Prerequisite   └── RightsRecord   └── ObservationQuality
       ├── TeachingCue
       └──< ActionSegment >── ModelVersion

TrainingPlan ──< TrainingBlock ──> MoveDefinition
TrainingSession ──< SessionEvent / UserReflection
MusicAsset ──< BeatAnnotation       AssessmentRubric（后续）
```

| 对象 | 核心字段 |
| --- | --- |
| MoveDefinition | ID、版本、舞种、名称/同义词、先修、建议 BPM、左右语义、教学提示、审核状态/审核者 |
| ReferenceTake | 视频本地引用、原始文件 hash、舞者/session ID、视角、入出时间、BPM/首拍、朝向/镜像、动作标签 |
| RightsRecord | 来源 URL、作者、表演者授权、素材许可、允许用途、条款版本与核查日期 |
| PoseFrame | 完整原始 PTS value/timescale、全部有效/无效观测、人体数量、ambiguity、关键点与 confidence |
| ActionSegment | 起止 PTS、候选类别、拒识状态、模型/数据版本、人工更正；不存成评分 |
| TrainingSession | 实际流程时长（含计划内休息、不含暂停）、计满段数、跳过事件、感受、速度、结束状态 |
| MusicAsset | 本地/授权目录/MusicKit 类型、可处理权限、BPM/downbeat 来源、媒体时间基、许可记录 |

**原型当前存储**：原创动作卡是可版本管理的 Swift 静态值；真实训练记录写入本地带版本 JSON，原子替换。损坏文件保留并阻止覆盖；视频姿态在成功完整分析后按用户选择导出 JSON。AIST++ 则使用 JSON manifest 加逐序列 `.raw.f64` / `.optimized.f64` 文件，保存 1,123,873 个时间帧的两层原值；不把全部关节点做成 UI 可观察对象。默认数据目录为 `~/Library/Application Support/HidanClub/Datasets/AISTPlusPlus/`，大文件不进入源码仓库或应用包。没有云端账户、服务器或数据库服务依赖。

AIST 基础名称来自 `choreography-names.json`，保留 sourceURL、访问日期及原拼写，按 `sBM + genre + choreography` 查询；Advanced Dance 不套用同号基础名。音乐 ID 可映射官方 BPM，House 为 110–135、步长 5，其余九舞种为 80–130、步长 10。BPM 不提供首拍相位，因此八拍区间是基于所选起始帧与源速度的练习辅助，不等同于自动识别原音乐节拍。

**正式版建议**：共享 Foundation 模型；业务元数据可采用 SwiftData（iOS 17/macOS 14 起）或 SQLite。若强调透明 schema、迁移、全文检索和外部工具，优先 SQLite + FTS5；若先做纯 Apple 小型个人应用，SwiftData 成本低。逐帧姿态与媒体放外部文件，用数据库记录路径/hash/索引，避免把长视频每个关节点做成可观察 UI 对象。未来按 session 分块顺序存储能降低内存，分块不丢帧、不抽样、不覆盖原始值。CloudKit 只在明确需要跨设备同步后加入，并另做媒体容量和冲突设计。

现有全帧报告保存在内存，因此长视频/高分辨率视频会增加时间与内存开销；本版未对长度做静默裁切。界面只降低刷新频率，不改变数据点。

## 6. Swift 架构与音乐

```text
SwiftUI scenes / views
  ├─ HidanCore: 动作、训练计划、组合规则、计时状态机
  ├─ TrainingStore: 训练状态与本地历史
  ├─ VideoService: AVPlayer、镜像显示、速度、A–B 循环
  ├─ MusicService: AVAudioEngine / PlayerNode / TimePitch
  ├─ AISTLibraryStore: 本地 manifest、全帧 Float64 序列与动作参考
  └─ PoseAnalyzer: AVAssetReader → Vision → 全帧 PoseReport
```

Mac 原型基线 macOS 14+，SwiftPM 构建 .app。当前工作站有 Swift 6.3.3 和 macOS SDK；活动开发目录是 Command Line Tools，尚未确认完整 Xcode/iOS SDK，故不能声称 iPhone / iPad 应用已经构建验证。HidanCore 无 AppKit 依赖，可用于未来 iOS/iPadOS；导入、相机权限、后台音频、屏幕方向与文件访问另做平台适配。

Vision 分析顺序读取全部解码帧，校正轨道旋转/镜像，保存原始 PTS；无检测保留空观测，多人保留 ambiguous 标记，不在不同人间静默跳转。取消时不发布半份报告，旧任务不能覆盖新任务。坐标归一化且原点左下，骨架复查与视频显示不是相机标定后的运动捕捉。

音乐使用 AVAudioEngine 合成原创八拍节奏，支持本地音频、独立速度/音高、音量与播放暂停。八拍视觉取音频渲染时间，不由训练倒计时猜测。本地曲目暂未自动检测 BPM/首拍；视频播放器和音频播放器也没有承诺共同时间基下的精准同步。A–B 视频循环是学习用途，仍可能有 seek 边界延迟，不能用于专业 sample-accurate 编排导出。

[Apple Developer Program License Agreement 3.3.6(D)](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)明确约束 MusicKit 内容下载、上传、修改及与其他内容同步（文档另行许可除外）。因此不能把 Apple Music 订阅曲目当作可随意解码、变速、配视频或训练模型的音源。MusicKit 以后只在具体用例和权限核查后设计。

## 7. 训练界面与合理训练

训练台采用常驻导航 + 主练习区 + 底部独立音乐条。第一屏突出今日目标、当前段落、大号倒计时和开始/暂停。侧边给一个重点提示、用力感记录和八拍格；详细课程/研究信息不挤入训练控件。

训练状态链：`idle → running ↔ paused → completed / stopped`。每段可跳过；已暂停时间和未练完的剩余段不虚构成完成量。系统休眠时暂停。历史保存真实流程时间，含计划内休息，不能标成纯运动时长或能量消耗。

原型可生成 10–45 分钟计划（UI 提供 10/15/20/30/45）：约 1/6 热身、约 1/10 放松并设置上限，其余分为基础动作与短休息；较长计划末尾加入熟悉动作自由连接。数字是可调整的产品规则，未作为个体化运动处方验证。时间分配和先修次序可查 HidanCore / PlanBuilder。

建议后续加入“今日可用时间、疲劳、酸痛/不适、昨日负荷、想练什么”四类输入，然后用透明规则先做负荷调整。用力感升高时允许减幅度、减速、延长休息；没有身体状况信息时不自动推高强度。[CDC 强度说明](https://www.cdc.gov/physical-activity-basics/measuring/index.html)用 talk test 和 0–10 主观努力说明强度；这只是一般活动强度参考，不是街舞训练疗效证据。本原型用力感为用户主观记录，不由视频估算。

基础版本排除倒立、power moves、强迫关节幅度与高冲击组合。后期进入 Breaking / 地板动作必须有专门教学、场地和能力筛选，且需要重新评估单目关键点适用性。

AIST++ 参考库可以浏览 Breaking 等完整舞种，但参考可浏览不表示其中所有动作适合直接跟练。训练计划导入应保留序列 ID、连续源帧范围、速度与来源质量标记；不能将舞种标签、BPM 或一次收藏当成能力评估。起止段和八拍选择不改写原序列，导出保留所选连续区间的每一个源帧。

## 8. 分阶段建设与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| 0：本次原型 | 原生训练台、16 动作卡、规则组合、音乐/视频工具、姿态导出、记录与调研 | 编译、核心行为测试、程序包启动与实际 UI 检查；无虚构能力 |
| 0.2：AIST++ 接入 | 全量 3D 标注与 100 基础动作名；动作库、收藏、逐帧/片段跟练与计划接入 | 数据无损校验已完成；本轮新增 UI 和训练行为按 VERIFICATION.md 单独验收 |
| 1：内容与数据 | 教师校对动作、授权多视角示范、个人动作档案、歌曲首拍标注 | 授权逐项明确；初学者能独立完成看/练/回看；真实视频观测质量审计 |
| 2：有限动作识别 | 3–5 类时序模型、负例、拒识、动作分段 | 跨舞者测试、每类指标、域差异报告；模型不能判断时明确拒识 |
| 3：可解释反馈 | 有教师量表的时序/顺序/局部运动指标 | 教师一致性与独立用户测试；错误反馈可追查到观测与模型版本 |
| 4：个性化与生成 | 熟练度/疲劳驱动训练、检索式组合、可选生成模型 | 先验证规则生成的用户价值，再证明生成模型带来改进；动作可做性需人工复核 |

本次没有安装第三方模型、调用付费 AI、建立云服务或下载课程；这些并非运行原型所需。后续投入最有价值的资源是少量授权、标注一致的真实示范与练习视频，以及一位能审核街舞动作与反馈的教师，而不是立即汇集数十万段来源不明的视频。

## 9. 尚未解决的明确问题

- 用户已确认 Mac 优先、后续 iPhone / iPad，并希望多舞种全部覆盖；具体熟练度、年龄与公开发行计划尚未确认。更多风格与高难度课程需另建内容与验证路径。
- 真实舞者、衣物、遮挡、地板动作、多人场景的准确度没有获得实测结论。
- 原创文字卡未经教师审核，不能替代示范或完整课程。
- 摄像头实时镜像/录制、同步双视频回看、自动节拍检测、从用户视频估计 3D、舞步分类、质量评分、跨设备同步尚未实现。AIST++ 3D 参考数据已实际接入，不与这些模型能力混称。
- 逐帧分析内存随视频长度增长；正式长视频支持需要顺序文件存储与中断恢复。
- 当前应用为本地 ad-hoc 签名原型，不是已公证的 App Store/公开分发版本。
